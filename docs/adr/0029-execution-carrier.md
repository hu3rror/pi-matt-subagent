# Execution carrier: subagents run in herdr-core terminals behind a two-value knob

> [ZH] 本 ADR 记录 `carrier` 这个执行载体决策（issue #50 的实现，落在 #51/#52/#53/#54/#55）。编号是 0029 而不是 issue 标题里写的 0028：0028 是本决策依赖的会话终端回收决定。摘要：`spawn`（默认）保持今天的管道子进程与进程内 research 子会话；`hc` 把每个子 agent 跑成 herdr-core 上一个有名字、可 attach、可 kill 的终端，结果对象不变。启动期失败：blocking 告警并回退 `spawn`，research 只在缺 `sh` 时回退（core 起不了终端就判该次 run 失败）；运行中丢失 core 则把该次 run 判失败并点名终端与 run id，绝不伪造空成功。`caller`/parent-death 一律不传——实测证明它们只在「pi 自己就在 core 终端里」时才有意义，回收改由会话结束时显式 kill（ADR 0028）。

A subagent used to be a piped child process owned by pi: nothing outside pi could see it, attach to it, or kill it alone, and a hard pi death left nobody able to tell whether it survived. herdr-core offers named, attachable, killable terminals on the same machine, so the execution can live there instead of in a pipe. The carrier is a **place to run**, not a new result surface: tool results, exit statuses, push delivery, and run status stay identical, and `spawn` stays the default so an upgrade changes nothing for a user without a core.

## Decision

- **One knob, two values, read at dispatch.** `carrier: "spawn" | "hc"`, default `spawn`, resolved through the ADR 0018 config pipeline (`src/lib.ts` `EffectiveConfig.carrier`) on every dispatch — flipping it needs no `/reload`. An unaccepted value degrades to the default and is flagged `[degraded]` in the config view, which is how the rest of the knobs behave (ADR 0018); no per-run warning is raised for it. The value also reaches the research factory, so both execution modes move together.
- **One port for core.** Everything the extension does against herdr-core goes through `HcClient` (`src/hc-client.ts`): `hc connect --json`, one JSON object per line over stdio, responses correlated by id, `AbortSignal` honoured, every failure classified as `unavailable` / `method-missing` / `protocol` / `killed` instead of thrown. A capability probe (`hello` → `generation`, `version`, `methods`, `features`) is what a caller branches on; a version whitelist is not. A generation change invalidates the cache. Wrapping it in a socket or named pipe would add a second transport to handle while the line protocol already covers stdio and leaves `--session` as the path to remote cores.
- **Blocking: a second `RunnerSeam` transport.** `src/blocking-carrier.ts` runs the prepared child as a two-line `sh -c` script in a terminal: `{ <pi invocation> 2> <err>; echo $? > <out>.exit; } | tee <out>` mirrors stdout to the screen and the file at once, and `exit "$(cat <out>.exit 2>/dev/null || echo 1)"` reports the child's own code from the sidecar (1 when the run died before writing it). It waits with bounded `terminal.wait` check-ins and hands the stdout appended since the previous one to the same accumulator `spawn` feeds, so a live run's usage moves while it runs; the check-in that finds the terminal ended drains the rest, and stderr is read back once. The terminal's recorded exit code drives the same completion path a process `close` event drives; `SingleResult` assembly is shared, not re-implemented.
- **Research: an implementation of the existing child-session factory.** `src/research-carrier.ts` returns the same `{ output, done, abort }` shape; `output` polls the two terminal files, `done` settles on the terminal exit code (non-zero rejects), `abort` kills the terminal. No new seam was introduced for research. The polled files are `<log>.terminal.out`/`.terminal.err`, never the run log: the runner's tee stays the log's only writer, and a carrier writing it directly would need that contract retired.
- **Failure policy splits by *when*, not by *what* — and the two carriers are not symmetric.**
  - Blocking, startup (core unreachable, probe failing, `terminal.run` erroring, no POSIX `sh` on PATH — including Windows without `sh.exe`): warn, name the cause, and fall back to `spawn` **for that run**. The user asked for a subagent, not for a core.
  - Research, startup: only a missing shell falls back (to the in-process child). A core that cannot take the terminal throws and that run fails. #50's blanket wording ("unreachable core falls back") is not what the research path does; whether to align it is a follow-up decision, deliberately left open here rather than settled by a doc.
  - Mid-run, either carrier (core lost after the terminal exists): fail the run with an error naming the terminal and the run id. The outcome is unknown and the command may still be running, so nothing is re-run and no empty success is fabricated.
- **Teardown is explicit, never inherited.** Terminals created by either carrier are recorded per session and killed on `session_shutdown`; a killed terminal that lands `finished` is removed (ADR 0028 owns the mechanism). The `caller` and parent-death options of `terminal.run` are deliberately *not* used — see below.
- **Identity.** Terminal name `sa-<first 8 of run id>`; labels `run=<run id>`, `kind=blocking|research`, `role=<role name>`. A terminal listing can be correlated with a run log, and killing the right one does not require guessing.
- **No metadata from core.** The protocol carries no model, thinking, usage, or cost fields. Those keep coming from the child's own JSON stream, so the accumulator, usage accounting, and cost display are untouched, and per-task `model`/`thinking` overrides behave the same on either carrier.

## Why `caller` and parent-death are unused, measured

`terminal.run` (core 0.1.20, generation 1) accepts `caller` ("Who is calling (`HC_TERMINAL_ID` inside a terminal)"), `parent` ("default: the terminal it is started from"), `outlive_parent` (default false: the child ends with its parent), and `die_with_parent` (documented as ignored, since children already end with their parent unless `outlive_parent`). Everything quoted below was read from `rpc.discover` on a live core and then measured through `hc connect --json`: `terminal.run` with the carrier's parameters, `terminal.get` on the result, and one `terminal.kill` + `terminal.wait` pair.

The probe, run from a pi that itself sat inside core terminal `t15` (`HC_TERMINAL_ID=t15`): with the carrier's exact parameters — `argv`, `cwd`, `env`, `name`, `labels`, nothing else — the new terminal came back `parent: null, die_with_parent: false`. The same call with `caller: "t15"` came back `parent: "t15", die_with_parent: true`.

So parent-death is opted into by the *`caller` parameter*, not inferred from the client's environment: as long as this port sends no caller, a child terminal has no parent and nothing in core ends it when pi goes away. Sending one would make teardown conditional on where pi was launched (nested under a core terminal versus an orphan in a plain shell, over SSH, or under a process manager) and would still leave the orphan case unhandled — two behaviours to reason about instead of one uniform `session_shutdown` kill. Hard death of pi (SIGKILL, crash) therefore leaks terminals; that residual is documented here rather than engineered around, because the recovery is the same one a human already has: `hc ls --all`, then `hc kill`/`hc rm`.

A related assumption is worth recording because ADR 0028's defect section still states it: a child started from an `hc connect` client is **not** nested under pi's terminal just because pi happens to live in one. Nesting follows `caller` alone.

## Considered options

- **Integrate with the legacy herdr TUI** — rejected: the carrier targets the core API; the TUI is a viewer for the same terminals, not a dependency.
- **`terminal.attach` as the output channel** — rejected: the first frame is screen text and only later bytes are raw output, so a file read stays the source of truth and attach stays a human affordance.
- **Parent-death instead of explicit teardown** — rejected for the measured reason above; the explicit kill is unconditional.
- **A version whitelist instead of a capability probe** — rejected: the protocol is preview, grows within a generation, and re-probes on a generation bump; a hard-coded version list would break on the first patch release that adds a method.
- **A socket or named-pipe transport** — rejected: `hc connect` over stdio already frames one JSON object per line, needs no platform-specific endpoint, and leaves `--session` for remotes.
- **A second poll loop for progress on blocking runs** — rejected: the check-in that already paces `terminal.wait` also reads what the run has written since the previous one, so a live run's numbers move on that cadence instead of on a timer of their own.
- **Worktree isolation** — out of scope: a legacy TUI feature absent from the core API. A carrier decides where a process runs, not what it has checked out.
- **Cross-machine execution and reads** (`machine.*`, the file API's remote target) — out of scope: the protocol exposes them, this carrier does not use them. `hc connect --session` stays the path to a remote core if that ever becomes a requirement.
- **OSC 7501 status reporting for subagent terminals** — out of scope: the carrier reads exit codes, not screen reports, and a terminal's status plumbing belongs to pi's own surface (title, footer, `/subagents`).
- **Installing or upgrading herdr-core** — out of scope: the extension degrades without a core, and provisioning one is the user's tool choice, not a side effect of loading a plugin.

## Consequences

- **Both carriers deliver the same result, with one failure-only field.** Tests pin whole-object parity through `RunnerSeam`, comparing everything but `runDir`: the same `SingleResult` shape, the same exit-code handling, the same usage. `runDir` is set only by `hc` on a run it did not finish successfully, because only `hc` has a directory to name; `spawn` never carries it.
- **Non-zero exit is a failed run, on both carriers**, so a crashing child is visible instead of reading as an empty success.
- **A terminal killed from outside pi lands the run `failed`, not `aborted`.** Measured: `terminal.kill` leaves the record `reason: "killed"`, `exit_code: null`, `signal: 1`, and `terminal.wait` reports `ended: true, exit_code: null`; a natural non-zero exit reports `reason: "exited"`, `exit_code: 3`. Only the abort lever (kill command, shutdown, wall clock) lands `aborted`. Mapping an external kill to `aborted` would need a carrier→runner channel plus a `reason` read in the failure path — the honest status is available either way, so the divergence stands, recorded here rather than silently smoothed.
- **A failed blocking run keeps its `pi-hc-run-*` directory; a successful one does not.** The directory holds the child's stdout transcript, its stderr and the exit-code sidecar, so a failure can be read after the fact instead of reconstructed from the tool result. Its path reaches the caller as `runDir` on the result, which surfaces in the tool result's `details`. Cleanup is the user's job: nothing sweeps old run directories, so a failure that nobody inspects stays in the temp dir. A lost core and an abort keep the directory too, and name it in the failure message or the warn line the caller already sees.
- **`tee` is a second external prerequisite, probed at startup.** Both `sh` and `tee` are resolved on PATH before a terminal is created; a host missing either warns and falls back to `spawn` for that run, so a host without `tee` no longer runs the child and reads back empty stdout. The probe is a PATH lookup, not a functional test: a `tee` that exists but cannot write would still fail inside the terminal. Research runs use the same script but keep their own rule — they fall back only when `sh` is missing.
- **A live `hc` run reports its numbers as it goes.** The bytes still reach pi from a file, but each `terminal.wait` check-in hands the stdout appended since the last one to the same accumulator `spawn` feeds, so the info box updates while the run is live; a run that ends on its own drains what the child wrote before it exited, so the screen, the file and the result still agree. The cadence is the blocking check-in, `BLOCKING_TERMINAL_CHECK_IN_SECONDS = 1`.
- **The research and blocking poll intervals are both provisional.** `RESEARCH_TERMINAL_CHECK_IN_SECONDS` and `BLOCKING_TERMINAL_CHECK_IN_SECONDS` are 1; no measurement backs either value yet.
- **An `hc` research child runs as its own `pi` process**, so it emits neither the in-process lifecycle announcement (ADR 0026) nor the out-of-process `PI_SUBAGENT_PARENT_SESSION` marker that blocking children get (ADR 0014). Under a loaded permission system, an `ask` raised inside it has no forwarding path today. Known gap, tracked separately; it does not affect results or run status.
- **Real-core coverage is a dev gate, not CI.** `scripts/hc-e2e.ts` drives a real pi session against a reused core and asserts the terminal, the read-back exit code and output, and the teardown; the binary is external and the protocol is preview, so CI keeps using a scripted child and a fake port.
- **The protocol remains preview.** Within generation 1 it only grows; a generation bump requires re-probing, which the port does on its next call after a lost connection.
- **`spawn` is untouched.** It is still the default, still runs where it ran before, and still returns what it returned before; `hc` is an opt-in that a user who has not installed core never reaches.
